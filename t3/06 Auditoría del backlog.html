Auditoría del Product Backlog

La lista de control de salud para las misiones de tu videojuego

❤️‍🩹 SALUD DEL BACKLOG: 0 % · PENDIENTE DE AUDITORÍA

Haz clic en cada criterio (o pulsa Espacio / →) a medida que audites las historias de usuario de tu equipo.

📜

1. ¿La historia tiene un propósito claro?

✓

Verifica que cada historia de usuario siga el formato conversacional de Connextra. Es el alma de la historia, conectando la funcionalidad técnica con el valor real para el jugador.

Como [ROL / JUGADOR], quiero [OBJETIVO / ACCIÓN], para [BENEFICIO / MOTIVACIÓN].

Ejemplo: «Como explorador, quiero un minimapa que revele las zonas visitadas, para sentir el progreso de mi aventura sin perderme».

🏆

2. ¿El Product Backlog está priorizado por valor?

✓

Lo que figura más arriba en la lista es lo que aporta mayor valor al núcleo jugable (core loop) y a los jugadores, no necesariamente lo más fácil o apetecible de programar. El Product Owner es el responsable último de este orden.

✅

3. ¿Están claros los criterios de aceptación?

✓

Cada historia necesita una lista de condiciones concretas y verificables que deben cumplirse para considerarla terminada. Sin criterios de aceptación claros, la Definition of Done es imposible de validar objetivamente.

Ejemplo para la historia «Quiero un doble salto»:

  • El segundo salto solo se activa si se pulsa el botón estando en el aire.
  • El segundo salto reproduce un efecto visual de partículas y un efecto de sonido propio.
  • El personaje no puede encadenar un tercer salto antes de tocar el suelo.
📏

4. ¿La historia es suficientemente pequeña (Small)?

✓

Una buena historia de usuario debe poder completarse dentro de un único Sprint. Si un elemento es demasiado grande (una épica), hay que trocearlo en historias más pequeñas y manejables antes de entrar al Sprint.

ÉPICA (DEMASIADO GRANDE)

«Crear el sistema de inventario»

➔
HISTORIAS DE USUARIO (LISTAS PARA EL SPRINT)

«Visualizar cuadrícula de objetos», «Equipar un arma activa», «Soltar objeto al suelo»…
